About EMR Enhancer

EMR Enhancer is a standalone, multi-user EMR built around context. A clinician opens a patient, writes a short narrative, and adds context to it in the form of element sets: small, reusable groups of fields (for example Vitals, Fever chart, or Snake envenomation). Each context added builds up the patient's trajectory. A trajectory turned into a reusable template becomes a pathway, and a pathway can itself be extended by adding more context. The system keeps everything clinicians enter, draws trends from it, raises only the alerts a named clinician has approved, supports analytics across patients, and can export a record as FHIR R4.


In short: context → trajectory → pathway → more context.


It is the system of record: records live in a shared database behind accounts and roles, with an audit trail, backups and a tested restore. It is a standalone EMR, not a plug-in for another system, and it does not launch inside one. Not a regulated medical device and not for real patients until your site's named clinician has signed off the safety review and the restore test has passed. Check your local health-data and medical-device-software rules before go-live.



What is new here

    

  1. Context first, structure added later. A chart starts as a plain narrative. Structure arrives only when someone applies an element set, so the record grows with the patient instead of starting from a fixed encounter form.
    2. 

  2. One timed-reading model behind every view. A repeating, timestamped row is the single building block. The same rows feed the flowsheets, the fever chart, the daily insulin grid, trend charts, the Summary, the ward board, the FHIR export and the analytics. A new chart means a new set definition, not new code.
    3. 

  3. Pathways that record, not enforce. A pathway is saved from a real case as a list of sets and can be extended and re-versioned. It holds no doses, bands, order or deadlines, so it cannot judge whether care was on time. Pathway status shows only whether data has been entered.
    4. 

  4. Safety by construction. No clinical number is pre-filled (ranges, targets, thresholds and insulin bands are typed by the clinician). Doses are free text, never calculated. A rule fires only when it is enabled and approved by a named doctor or admin. Unverified codes never reach the export. Every latest value is shown with its age so a stale reading cannot look current.
    5. 

  5. AI drafts, people approve. A model can draft a set, a pathway skeleton or a rule from a clinician's plain words, but it never approves anything, never sees patient values, and never supplies a dose or threshold the clinician did not type. AI runs on the server, is de-identified, and is off by default. The system is fully usable with no model at all.
    6. 

  6. Controlled content life cycle. Content (sets, pathways, rules) is requested at the bedside, drafted, reviewed by an informatician who is never the author, and can then be shared through a public marketplace as versioned, hash-pinned, signed packages. Installed marketplace content is read-only; it is extended only by composition (adding other components beside it) or by making a labelled local fork. A verification badge travels with the content everywhere, including FHIR Provenance.
    7. 

  7. A record you can trust. Signed notes are read-only; a correction is a new note with a reason. Nothing is silently overwritten or deleted, and an append-only audit trail shows who changed what and when. Errors are marked "entered in error", not removed.
    8. 

  8. Export separated from the data model. FHIR R4 is a final step that reads a record, so a country or hospital can add its own profile without redesigning sets, charts or pathways.
    9. 




What has and has not been shown

Delivered by the build: a patient-centred shell; element sets, repeating readings and clinician-defined pathways; a rule evaluator with no shipped rules and a human approval gate; a server with database, REST API with validation and versioning, accounts and roles, append-only audit, patient and encounter records; live multi-user refresh, a ward board and handover; shared analytics with small-count protection; the content review queue and marketplace; an automated safety test pack; and a deployment with backup and a tested restore.


Not claimed: that it improves outcomes, saves clinician time, or is accepted by any regulator or national programme. Those need evidence from real use. Peer review by informaticians is not regulatory approval, and a FHIR export is not conformant to any national profile until that profile is added and validated.


Evidence worth collecting once running: time to chart a bedside set compared with the current system, share of fields left empty, FHIR validator pass rate, how often pathways are reused or edited, alert acknowledgement versus override rates, and clinician feedback on whether alerts are trusted and not noisy.

Can SMART on FHIR apps work with this EMR?

No, by design. SMART on FHIR lets an app run inside, or alongside, an EHR: the app is registered with the EHR, authorized with OAuth 2.0, and then reads and writes through that EHR's FHIR API. EMR Enhancer is its own system of record, so it takes neither role.


    

  • As a SMART app inside Epic, Oracle Health or similar: no. There is no SMART launch, no FHIR read of another system and no Send-to-EMR. Running as an add-on forces either double entry or a fragile mapping from another EMR's data into this model, and the value of this system comes from owning that model.
    • 

  • As a platform other SMART apps launch from: no. The server has its own REST API for its own interface, not a FHIR REST API, and no SMART authorization server or discovery document.
    • 

  • What does exist: a one-way FHIR R4 export (a real Patient, Encounter-based resources, Composition, Observations, CarePlan, Provenance) and CDS-Hooks-shaped alert cards as export. Nothing is imported from or written to another EMR, and the marketplace carries content definitions, never patient data.
    • 



If a specific hospital integration is ever required


Treat it as a new, separate project. It would need a FHIR API layer over the stored records and a SMART v2 authorization server (SMART v2 is the current baseline for US ONC certification); a CDS Hooks service built on approved rules; or SMART launch plus a mapping from the host EHR into sets if embedded. Coverage would be limited to what element sets map to, and apps expecting US Core or other profiles would need those profiles added first.

Core ideas

Element sets


A set is a titled list of fields with types (text, number, date and time, select, yes/no, duration). Kinds: disease (such as time from bite to antivenom), care (ongoing monitoring such as Vitals or HbA1c), template (a note structure), pathway (a bundle of sets) and custom (generated or your own). The system has no hidden clinical logic beyond what a set declares.


Single fields and repeating readings


Most disease fields are entered once per encounter. Care sets have repeating readings: each row has a timestamp and values, kept in time order, and several rows form a trend. Readings are stored as their own records, so two staff can add readings to one patient at the same time.


Direct sets and the Quick bar


Direct sets (Vitals, Fever chart, Insulin chart, HbA1c, Sliding scale) need no diagnosis or narrative. A nurse or doctor opens a patient and starts charting with one tap.


Context and trajectory


Context is what is known about a patient at a point in time. Applying sets adds it. As context accumulates and readings are added, the patient forms a trajectory: the sets applied, when they were added, and how values change. Charts, flowsheets, the Summary and handover are views of it.


Pathways


A pathway is a trajectory turned into a template. Save applied sets as my pathway keeps a patient's sets as a reusable pathway, such as DKA, Snakebite or Fever monitoring. Applying it adds its member sets and records {pathway, version, start time} on the patient. A pathway can be extended and saved as a new version; a patient keeps the version they started with. Pathways store set references only: never values, doses, bands, thresholds or required order. Applying never deletes data, and removing a pathway never removes sets or entered values.


Context filter and suggestions


The sidebar narrows sets and pathways by context and floats frequently used ones to the top. If AI is enabled by an administrator, it can suggest set and pathway ids from the narrative. Suggestions are only offered; nothing is added until a clinician chooses it.



Trends and views

    

  • Trajectory charts for numeric readings over time, with optional low, high and target lines that the clinician types. None is supplied.
    • 

  • Vitals flowsheet: parameters down, time across, newest on the right, blood pressure shown systolic / diastolic. Values outside a range the clinician typed are shown in red.
    • 

  • Fever chart: temperature over days with a per-reading unit (°C or °F), optional pulse as a second series, and a threshold line only if one is entered. The unit switch changes the drawing only.
    • 

  • Daily insulin record: days by slot (pre-breakfast, pre-lunch and so on) with glucose, dose as given and who gave it, a daily glucose summary and a target band only if entered.
    • 

  • Intake and output as another timed-reading set.
    • 

  • Derived intervals such as bite to antivenom or arrival to insulin, shown with a colour badge from the set's own thresholds.
    • 

  • HbA1c due badge showing days remaining or overdue for the follow-up date entered.
    • 

  • Ward board and handover: every patient with latest values and their age, pathway status and active alerts, refreshed live. No value is shown without how old it is.
    • 




Alerts (decision support)

Seed sets ship with no rules. A rule is a plain comparison against a threshold that a clinician or institution types in, with an indicator of info, warning or critical. A rule runs only once it is enabled and approved by a logged-in doctor or admin; the server stamps who and when. Alerts are prompts, not orders, and can be acknowledged. Acknowledgements and approvals are server records.


AI-drafted rules: a clinician can type a sentence and a model drafts the rule. The drafting model sees only field ids and labels plus that sentence, never patient values. A draft is rejected if its field is not in the set, its operator is not on the allowed list, or its threshold is not a number. The clinician edits and approves it; the model never approves. There is no live AI "second look" at the bedside.


Alerts such as "no reading for N minutes" exist only where a clinician-approved rule says so. Software that raises clinical alerts may count as medical-device software under local rules, so check before real use.



Content life cycle and marketplace

The engine (shell, charts, rule evaluator, FHIR export) is stable. Clinical content changes often and differs by place, so it has its own controlled life cycle.


    

  1. Request and draft (clinician): describe a need in plain words. AI drafts a set, pathway skeleton or rule, saved as an unapproved local draft.
    2. 

  2. Review (informatician, never the author): an automatic lint checks schema, ids, allowed operators, absence of patient data and codes against the verified table, then a human checklist follows. Approval, reviewer and time are stamped by the server. Two reviewers are recommended for anything containing rules or protocol bands.
    3. 

  3. Marketplace (any facility): approved content is published as versioned, hash-pinned, signed packages in a public GitHub registry. A facility browses, previews and installs it read-only.
    4. 



Four content rules


    

  • Local is free: a facility or clinician can create and edit its own sets, pathways and rules.
    • 

  • Marketplace content is usable: browse, preview, install and apply it to patients.
    • 

  • Installed marketplace content is read-only, enforced by the server (edits and deletes are refused), not just hidden. A change arrives only as a new published version.
    • 

  • Extension is composition: add other marketplace components next to it, or build a local pathway that lists pinned references. The package itself is never altered.
    • 



Forks, disabled rules and badges


    

  • Fork: to change marketplace content, make a local copy under a new id. It is labelled local and unreviewed and keeps a link to its source.
    • 

  • Rules and protocol bands arrive disabled. A local doctor enables them, because reviewers elsewhere cannot know a ward's units, populations or workflows.
    • 

  • Badges appear on set cards, notes, the Pathway tab and in FHIR Provenance (package id, version, hash, tier): Marketplace-verified (hash and signature checked at install, not editable), Local reviewed (approved in this facility's queue, version frozen) and Local draft (anything else, including AI drafts and forks). "Verified" means peer-reviewed, not approved by a regulator.
    • 



Trust and safety of packages


    

  • GitHub provides hosting, history and review, but not automatic immutability or signatures, so trust does not rest on it: each version is pinned by SHA-256 in a signed index, the maintainers' public key is pinned in server config, and the server verifies both at install.
    • 

  • Packages contain definitions only: no patient data, names, MRNs or free-text cases. Any rule threshold, band or dose-like text must carry a citation.
    • 

  • Installs never upgrade existing patients automatically. A withdrawn version shows a warning on patients who used it; nothing is deleted.
    • 

  • The server fetches only from the allow-listed registry. Sites with no internet install from a package file with the same hash, signature and lint checks.
    • 

  • Code is MIT licensed. Each package declares its own content license, and SNOMED CT and LOINC licence terms apply to codes and display names.



Codes and FHIR

    

  • Fields have no codes by default. A user adds a SNOMED or LOINC code and its display exactly as shown in the official browser and attaches it to a field. Codes live in shared reference data, so a verified code is available to the whole facility.
    • 

  • Verify live asks tx.fhir.org whether an attached code exists. A valid code can still be the wrong concept, so compare the display text.
    • 

  • The FHIR R4 bundle is built per patient: a real Patient (from registration, with MRN), a Composition from the notes, a Condition for each disease set, an Observation, Procedure or MedicationAdministration for each value or reading row, a CarePlan for each pathway, and Provenance for content. Unverified codes are left out and plain text is kept. Doses are copied exactly as typed. Sliding-scale protocol data is never read into the bundle.
    • 

  • Export only. Nothing is imported from or written to another EMR.
    • 

  • No national profile. The export uses plain base FHIR R4. It is not profiled to US Core or any national or regional profile and claims no conformance. Do not use it to exchange real patient data until the profile your jurisdiction requires is added and the output validated.
    • 



Adapting to a national profile


The profile step belongs to whoever deploys this open source project. Export is a separate step that reads a record and builds the bundle, so a profile can be added without changing sets, pathways, charts or analytics. A deployment would typically bind the codes the profile requires, map registration and identifiers to the profile, add element sets for any mandatory elements the record does not yet capture (values not entered are left out, never invented), and validate the bundle with a FHIR validator.



Analytics

Pick what to analyse: all patients, one disease, one pathway or one care set. Only patients who use the chosen item are counted, and only relevant cards are shown. For snake envenomation these include time to antivenom and adverse outcomes by delay band; other disease sets show their own timing and outcome counts; care and pathway scopes show set usage and readings per day. Analytics read the shared store, and small counts are suppressed so individuals cannot be picked out. Everything is descriptive: no causal claims and no judgement of whether care was adequate. Synthetic demo data can be loaded in a demo environment.



Accounts, roles, audit and your data

    

  • Login and roles control who can chart, sign notes, approve rules, review content and administer the system. Only a doctor or admin approves a rule; reviewing content is an informatician role held by someone other than the author.
    • 

  • Append-only audit trail records who viewed or changed what and when. Corrections are amendments with a reason, and mistakes are marked "entered in error", never silently overwritten or deleted.
    • 

  • Shared database holds patients (with MRN and encounters), cases, readings, sets, pathways, codes, rules, approvals and acknowledgements. The browser keeps only a cache for responsiveness, shows save status and retries when offline. Browser storage is used as the record only in Demo mode with synthetic data.
    • 

  • Backups and a tested restore are part of go-live. The system should not hold real patient data until a restore test has passed.
    • 

  • One-time import brings in data from the earlier browser prototype, with a conflict screen where records differ.
    • 

  • Security hardening covers sessions, input validation, access control and deployment settings. Review it against your local health-data law before use.
    • 

  • Each repeating table is limited to 500 rows per patient set.



AI features (optional, server-side)

AI supports schema generation, rule drafting and set suggestions. It runs on the server with the provider key held there, is off by default, and works on de-identified input only. Identifiable patient data must not go to an external model provider without a data processing agreement. Any code an AI suggests is unverified until a person checks it, and nothing it drafts is used until a clinician or informatician approves it.



Safety principles built in

    

  • Records guideline-based care; does not enforce it. Pathways are bundles of sets with no required order, timing or steps. The clinician decides what to do and when; the timestamps show what happened.
    • 

  • No default clinical numbers: reference ranges, targets, thresholds, protocol bands and glucose ranges are all typed by the clinician.
    • 

  • No dose calculation: doses are free text exactly as given, never summed, converted or recommended.
    • 

  • No unverified codes in outputs, no alert without a named approver, and no silent deletion by pathways.
    • 

  • Entered values are stored as entered; charts and unit switches change only how they are drawn.
    • 

  • Every latest value shows its age. Summary and the Patients list show data presence, never adequacy of care.
    • 

  • Signed notes are read-only; changes are amendments with a reason.
    • 

  • Installed marketplace content cannot be edited, and its rules arrive disabled.
    • 

  • An automated safety test pack checks these rules before each release.
