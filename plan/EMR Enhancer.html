EMR Enhancer: one engine, content as data

A small, stable engine runs clinical content that clinicians and informaticians write, review and share. Pick your audience.

Status, plainly: this is a plan and design, not a running system. The Analytics app is built; the EMR engine is not yet. “Not for clinical use” stays until a named clinician signs off.

The patient journey and the two apps

Rule of separation

All analytics run only in the Analytics app. The EMR just exports.

One registry

One signing key, two small clients. Each app installs only its own kind of item.

The test of the design

Someone outside the team writes one JSON package and it works, with no app code touched.

Engine and content: the core idea

Why it scales

The tenth specialty costs the same kind of work as the second: write, lint, review. The engine does not grow.

Same pattern as your Analytics engine

AI only proposes, a person approves, source wins, readiness is checked first, audit is tamper-evident.

Honest limit

“Any speciality” depends on a small closed set of view types being enough. Real specialties will test that.

For clinicians: what you do and what is protected

What you do
  • Say what must be recorded and shown
  • Review wording and content of a pathway
  • Approve, request changes or reject
  • Sign the content off before real use
What you see
  • Ward board, handover, flowsheets, summary cards
  • Data as recorded, never a judgement of care
  • A label on every form: who reviewed it, which version
What the software never does
  • Pre-fill a dose, threshold or band
  • Calculate or add up free-text doses
  • Fill in a code for you
  • Fire a rule nobody approved
Trust labels on content

marketplace-verifiedlocal-reviewedlocal-draft Verified means peer review, not regulatory approval. A draft cannot be applied to a real patient.

Safety stays on the screen

The “Not for clinical use” banner stays until a named clinician signs off. Early use: training, demos, ten synthetic patients, pilots.

For informaticians: elements, coding, layers, profiles

Profile label wording

“Built for profile X vN, checked on synthetic data on date D.” Never “compliant”. A required code the user did not enter is listed as a gap, never invented.

Authoring

Write a JSON package, run the lint locally, open a pull request, get reviewed. Closed role list: time, quantity, category, status, text, actor, link.

Open decision

Layer merge rule (decision 43) needs your answer before profiles are built.

For programmers: data flow, rules, build order

Engine rules
  • E1 code never names a clinical set, field or option
  • E3 new type = pure function + made-up-set test + validator + doc line
  • E4 view data holds ids, labels, windows only
  • E6 viewing writes nothing
  • E8 access block first, default deny
  • E9 no analytics in the EMR
Guards
  • Guard test fails if hand-named ids creep into code
  • Role × route × element matrix, generated
  • Shared files (compatibility(), lint) checked identical in CI
  • Index signed with ed25519, hash of canonical JSON
Task size

273 micro tasks: one file, one concern, about 60 words, at most 90 new lines. One task per chat.
