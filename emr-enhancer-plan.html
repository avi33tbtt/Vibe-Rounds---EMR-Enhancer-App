Architecture decision record · ADR-001

Accepted 21 Nov 2026

Decision. EMR Enhancer is a context-aware clinical documentation and trajectory system. Its system of record is a proprietary composable model (element sets · pathways · applied composition · repeating observations · narrative). SNOMED CT and LOINC are bound and verified inside that model. FHIR R4 is the interoperability boundary (export now; API/import later), not the internal form engine. Integrations (drug–drug interaction, other EMRs, national registries) are done by mapping at the boundary.

Context

The first idea was a full contextual EMR built on FHIR SDC (every form a Questionnaire, every save a QuestionnaireResponse). In practice that fought the product's core ideas: additive composition of small modules, partially applied/removable pathways, longitudinal repeating observations, and fast clinician UX.

Options considered

A · FHIR-native (SDC)B · Proprietary model + FHIR export ✔C · openEHR archetypes
IdeaForms = Questionnaires; storage = FHIR resourcesOwn element sets, pathways, repeating rows, rules; FHIR generated on the way outReference model + governed clinical archetypes
StrengthInterop by constructionFast iteration; clean composition/trajectory; full UX controlExcellent longitudinal, versioned content
CostHeavy forms; composition and pathways awkwardWe own the mapping and must prove export qualitySteep learning curve; different tooling/ecosystem

Reasons

  • Fit. Composition, pathways-as-bundles and trajectory are first-class in B and awkward in SDC.
  • Standard practice. Mature systems keep a rich internal model with standards at the edges. OpenMRS keeps its own concept dictionary mapped to SNOMED/LOINC; Epic/Cerner are not “FHIR all the way down”. openEHR itself is a purpose-built internal model, so this choice follows the same pattern rather than contradicting it.
  • Niche. The product is a documentation + trajectory layer, not a general EHR clone. It can sit beside or feed OpenMRS/openEHR via FHIR.
  • Reversible at low cost. Adding a real interface later changes the boundary, not the core.

Misconceptions this decision rests on correcting

  • “Only FHIR lets me use SNOMED/LOINC.” False. They are independent terminologies; FHIR is one carrier. Bindings live on each field as {system, code, display}.
  • “Only FHIR enables drug–drug interaction checks.” False. DDI engines take drug codes (RxNorm/ATC/local) plus patient factors. Map active meds outbound at call time; store the resulting alert in our model.
  • “Only FHIR gives interoperability with EMRs and registries.” False. Interoperability is about interfaces and payloads at the boundary (FHIR, HL7 v2, CDA, custom) — not internal storage.
  • “Proprietary means reinventing openEHR/OpenMRS.” Only if we try to become a general EHR platform. We are not.

What this changes in the build

  • Build-by-hand creator: each field now has an optional terminology binding (system · code · display) with a live Verify button. Editing/saving a set preserves bindings, rationale and required flags (previously dropped on edit). Changing a code drops its verified status automatically.
  • LLM generator: the model only proposes candidate bindings, tagged source:"llm" and element-set provenance {by, at, reviewed:false}. The prompt tells it to leave a binding empty when unsure and forbids doses, target ranges and protocol thresholds. A preview table shows each proposed binding and a Verify bindings step before apply/save. Dose/threshold-like text is flagged for review.
  • Verification rule (stricter than before): verified = code found on the terminology server and the LLM/user display matches the server display. A real code with the wrong meaning is flagged as display mismatch and stays unverified, so a hallucinated-but-existing code cannot reach FHIR as a Coding.
  • FHIR export: unchanged in behaviour (verified codes only) and now explicitly the boundary — see the mapping below.

Revisit this decision if

  • A funder, hospital or regulator requires Questionnaire/QuestionnaireResponse as the stored form model.
  • Content governance across vendors becomes the main goal (then evaluate openEHR archetypes).
  • The scope grows toward orders, billing and ADT as a full hospital EMR (then evaluate contributing to OpenMRS rather than building).

Architecture decision record · ADR-002

Accepted 21 Nov 2026 · refines ADR-001, does not reverse it

Decision. Element sets can be authored two ways: the simple proprietary builder / LLM generator, or imported as FHIR SDC Questionnaires (standards-based or curated packs). Both normalise into the same internal element-set model, so they can be mixed in one case, versioned, bound to codes and exported. The internal model stays the system of record; SDC is an additional authoring and exchange format, and QuestionnaireResponse an additional export.

Why this is compatible with ADR-001

ADR-001 warned against making Questionnaire the only way to define a form or the stored form model. This keeps both: SDC content is converted on import, so composition, pathways and repeating observations keep working on it.

What is enabled in the demo

  • Import a Questionnaire (paste, file or URL) → element set. Groups, string/text/integer/decimal/quantity/boolean/date/dateTime, choice with inline options, units, item codes (SNOMED/LOINC become field bindings, still unverified until checked).
  • Export any set as a Questionnaire: the original unchanged if untouched, otherwise one generated from the internal model (verified codes only).
  • QuestionnaireResponse in the FHIR Bundle (for SDC-sourced sets, all sets, or none), nested to match the group structure, referencing the Questionnaire canonical + version. Observations are still exported as before.
  • Re-importing the same Questionnaire URL creates a new set version (history kept); editing an imported set marks it “modified” so export no longer claims the original.
  • Curation label on imported sets (publisher / pack name, “unreviewed” until a human reviews it).

Known limits (flagged on import, not silently dropped)

  • Conditional display (enableWhen), calculated/initial expressions, value-set options (answerValueSet is not expanded; captured as text), multi-answer (repeats), attachments/references.
  • Date-only items are stored as date-times and exported back as dates. Codes from systems other than SNOMED/LOINC are kept on the field but not verified or exported as bindings (to be lifted by ADR-003).
  • SDC has no trajectory concept: any timestamped repeating series is an internal feature; in a QuestionnaireResponse the values collapse into plain answers (timestamps live on the Observations).

ABDM (India): what this does and does not give you

  • The ABDM FHIR Implementation Guide (NRCeS for NHA) defines profiles on output: Composition-based clinical artifacts (e.g. OPConsultRecord, DiagnosticReportRecord, DischargeSummaryRecord, PrescriptionRecord, WellnessRecord), DocumentBundle, and resource profiles (Observation, ObservationBP, Encounter, MedicationRequest …). The pages reviewed list no Questionnaires.
  • So compliance is an export-profile concern, not a form-definition one. A curated, ABDM-aligned form pack can be imported and labelled, but the label is informational: the app never emits meta.profile or claims conformance without validation.
  • Genuine ABDM output needs a Document Bundle with the right Composition type and sections, Practitioner/Organization/Encounter, ABHA-related identifiers, and validation against a chosen IG version (6.0.0 is the published release; 6.5.0 is draft and 7.0.0 is in development as of this review). That is its own work item (p5-5), done against a real HIP/HIU need.

Architecture decision record · ADR-003

Accepted (design) 21 Nov 2026 · refines ADR-002 · revives “more code systems” from the parked list

Decision. The same create / generate screen serves both authoring modes and makes two independent choices. (1) Output: by default the result is an internal element set (as today); with the checkbox “Also author as FHIR SDC Questionnaire” ticked, the Questionnaire is the authored artifact and is normalised into the same internal element set (ADR-002), so it still composes, versions, joins pathways and exports. (2) Coding: the author picks which code systems to bind (SNOMED CT, LOINC, RxNorm, ICD, …) or skips coding entirely — in either output mode, globally or per field. The picker and the verification are identical in both modes; only the carrier differs (internal bindings[] vs item.code[]).

Code-system registry (replaces “one SNOMED or LOINC binding per field”)

SystemTypical roleVerificationNotes
SNOMED CTFindings, conditions, procedures, coded answersTerminology server lookup (tx.fhir.org today)Licence terms differ by country/affiliate — confirm before publishing content packs.
LOINCMeasurements, lab and panel itemsTerminology serverFree licence with attribution.
RxNormMedications (US-centric)Terminology server / NLM RxNavOutside the US, ATC or a local drug table may be the practical choice; confirm against the target registry.
ICD-10 / ICD-10-CM / ICD-11Diagnosis classification, reporting, billingICD-11: WHO ICD API. ICD-10 variants: server if hosted, else local tableSeparate systems; never mixed under one label. Mainly bound at disease-set level, not on observation fields.
ATCDrug classServer if hosted, else local tableClassification, not a concept dictionary.
UCUMUnitsExisting known-safe mapAlready used by the exporter.
CPTProcedure billing (US)Local tableProprietary (AMA licence). Off by default; confirm licensing before enabling or shipping any content.
LocalSite-specific codesLocal tableNever exported as a standard Coding system.

Each registry entry is configuration: {uri, label, roles, verifier, licenceNote}. A system with no available verifier can still be bound but stays unverified, and unverified codes are never emitted as Coding (invariant unchanged).

Rules

  • Skipping is a first-class choice. An uncoded element set is fully usable in the EMR. It is flagged “uncoded” in the marketplace and can only be matched by analytics through its exact element id (ADR-004).
  • Several bindings per field (e.g. LOINC and SNOMED for one concept), each verified separately; export puts every verified one in code.coding[].
  • Role guard. The picker warns when a system does not fit the field (e.g. ICD on a numeric observation, LOINC on a diagnosis). Warning only; the author decides.
  • ICD, yes — as a classification. It is optional, bound to the diagnosis a set is about, and verified like the others. No automatic SNOMED→ICD derivation unless via a published map, shown as “mapped (source, version)”, never as “equivalent”.
  • LLM generation proposes bindings only for the systems the author ticked, tagged source:"llm", empty when unsure, then the same verify step.
  • SDC mode shows, before generation, what SDC cannot yet express here (enableWhen, calculated expressions, answerValueSet expansion — see ADR-002 limits) so the author knows what will not be honoured.

What this changes in the build

  • Field model: binding → bindings[] = {system, code, display, source, verified}; existing single bindings migrate to a one-item list.
  • One create screen: [ ] Also as SDC Questionnaire · Code systems: [SNOMED] [LOINC] [RxNorm] [ICD-10/11] [ATC] [Local] [None]. Per-field override and “skip this field”.
  • Verifier is chosen per system from the registry; the existing display-match rule applies to all.
  • Order matters. Do this migration before the marketplace package format is frozen; changing the binding shape after content is published means migrating published packages. Ship it as a new migration, never by editing applied ones.
  • Terminology host. A server that only talks to the registry must also be allowed to reach the terminology server: two named hosts from configuration, nothing else. Public terminology servers are best-effort and intended for testing; production should use a configured or licensed server, with verified results cached.

Architecture decision record · ADR-004

Accepted (design) 21 Nov 2026 · extends the content lifecycle in the build plan (Phase 6)

Decision. Reusable contextual elements (element sets), pathways and analytics are published to a marketplace backed by a public GitHub registry, organised by patient journey. Content is submitted, checked, tested, peer reviewed and released; EMR users browse and install released versions and the Suggest buttons recommend them from case context. The internal model stays the system of record (ADR-001); packages are installed into it. Patient data never travels this way.

Marketplace by patient journey

StageIn marketplace?ContentWhy
1 · RegistrationNo. EMR-localPatients, MRN, encounters (p4-5)Site-specific identifiers and personal data. Package lint refuses a registration kind and identity-like keys.
2 · Clinical data recordingYesElement sets (disease · care · template), pathways, rulesReusable clinical structure; browsed by specialty, condition, code system, uncoded flag.
3 · Clinical analyticsYesAnalytic definitionsAn analytic depends on elements, not on a pathway, so one analytic works on every pathway carrying those elements.

Orders, MAR, ADT and charge capture (p5-3) are not marketplace content by default: operational and site-specific, like registration. Revisit if a real need appears.

Analytics compatibility

  • An analytic declares requires: elements by setId + field, or by verified code with expected type and UCUM unit.
  • CI builds a compatibility index. Pick an element set or pathway → all compatible analytics; pick an analytic → all compatible sets and pathways. A pathway satisfies the union of its pinned members.
  • Match kinds are always shown: exact · via code (same verified code, same type and unit) · partial (missing fields listed). Units are never converted: a unit mismatch is reported, not matched. Uncoded elements match by exact id only.
  • Analytics are declarative definitions run by the EMR's own evaluator; the marketplace ships no executable code. Thresholds inside an analytic are parameters that ship blank (“needs local setting”) and need a citation to pass lint. Results use the same small-count masking as other analytics.

Content rules (adopted from the build plan)

  • Local content is free: a facility can create and edit its own.
  • Installed marketplace content is read-only, enforced by the server (not only hidden in the UI). It changes only by a newer published version.
  • Extension is by composition: add other components beside it, or build a local composite pathway of pinned references. To change content, fork it: new id, labelled local draft, link to the original kept.
  • Rules and protocol bands in any package arrive disabled; a local doctor enables them (server stamps who and when). Seed sets ship with zero rules.
  • Installs never auto-upgrade cases; a case keeps the version it started with. A withdrawn version shows a warning on cases using it and blocks new use; nothing is deleted.
  • An unapproved draft is never applied to a real patient's case.

Trust model

Tier shown in the appMeaningEditable?
Marketplace-verifiedInstalled from the registry; signature and hash checked at installNo (fork instead)
Local reviewedApproved by an informatician at this facility; version frozenEditing makes a new draft version
Local draftAnything else, including AI drafts, imports and forksYes
  • Index metadata beside the tier (not extra tiers): automated checks passed, synthetic tests passed, number of independent reviewers, evidence link when one exists. “Verified” means peer-reviewed, never approved by a regulator.
  • Automated checks (CI and local lint, one shared script): schema, SDC structure, every bound code verified (exists and display matches), no dose / threshold-like text without a citation, no executable content, no patient-like strings, licence present, hash computed.
  • Review: an informatician who is never the author; two reviewers for anything with rules, bands or dose-like text; reviewer and time stamped by the server, not typed.
  • What GitHub does and does not give. It gives hosting, history, pull-request review, CODEOWNERS and CI. It does not by itself give immutability or signatures. So trust does not rest on GitHub: every package version is pinned by SHA-256 in a signed index, the public key is pinned in the server config, and the server verifies signature, hash and lint at install. Protect the main branch and check GitHub's current documentation on tag protection and immutable releases.

Using it inside the EMR

  • Roles: browse is open to clinical roles; install is for informatician and admin; a doctor can request an install (audited). A site setting sets the minimum installable tier.
  • Install: fetch from the one allow-listed registry address, verify, lint, store read-only and pinned. Hospitals without internet install from a package file that passes the same checks. Installed copies keep working offline.
  • Suggest buttons: deterministic eligibility from each package's appliesWhen (applied sets, diagnosis codes, narrative terms matched locally) with redundancy suppression; labelled installed or in marketplace, with tier badge. Nothing is applied or installed without a click. An LLM may only rank or explain, de-identified and off by default. Compatible analytics are suggested the same way.

Risks and limits

  • Public repo = no patient data, ever; fixtures are synthetic and lint rejects identifier-like strings.
  • Licensing: SNOMED CT, ICD, RxNorm and CPT terms must be checked before codes and displays go into a public repository. Each package declares its content licence.
  • Regulation: distributing decision-support rules to many facilities may make the publisher responsible under medical-device-software rules. Peer review is not regulatory approval. Check before the first public release.
  • Governance is the real work: who reviews, conflicts of interest, recall response time, key rotation and key loss. The repo enforces the process but cannot supply reviewers.
  • The index is a static file that can be mirrored, including by a private hospital mirror.

Evaluated and deliberately not in the plan. Revisit only when a real use case or partner appears.

  • More code systems — un-parked 21 Nov 2026, now ADR-003 (items p1-11, p1-12): registry with verifier per system, several bindings per field, ICD as an optional diagnosis classification, local codes against a local table.
  • LIS integration (HL7 v2 orders/results). Skipped. Doctors view lab results in the LIS directly.

  • Add-on mode inside another EMR (SMART on FHIR launch, Send-to-EMR). Decided against in the build plan: it forces double entry or a fragile mapping. Revisit only for a specific hospital integration, as a separate project.

  • Read-only FHIR import / “External results” (paste a Bundle → pull from a configured FHIR server → subscriptions). Parked. If revived: store raw resources as immutable JSONB with source and version; never merge them into element-set fields; a clinician links patients, with no auto-matching; show imaging as links only.

Backend stack

Node.js + PostgreSQL, flat repository root, numbered SQL migrations that are never edited once applied. Built per the build plan: versioned rows with optimistic concurrency, append-only observations and audit log, element-set versions as immutable rows, scrypt password hashes, server-side sessions, CSRF tokens, one permission table enforced on every route, and a restricted database role. Browser keeps a cache-first Store with an ordered write queue; localStorage is for Demo mode with synthetic data only.

Design invariants (never relax)

  • Not for clinical use until independently reviewed and validated.
  • No pre-filled doses, therapeutic thresholds or protocol bands from an LLM.
  • Deterministic logic decides eligibility; AI may only rank or explain.
  • Codes are verified before they become Coding in FHIR exports.
  • Clinical data is never hard-deleted (use entered-in-error + reason later).
  • A pathway or set is a starting structure, not a lock-in.
  • FHIR R4 patient data is export-only for now (not a live SMART/EMR integration). Questionnaire definitions may be imported (ADR-002).
  • The internal element-set / pathway model is the system of record; FHIR is the boundary, never the form engine (ADR-001).
  • Terminology bindings live in the model; a binding is verified only if the code exists and its display matches.
  • LLM-proposed codes are candidates (source:"llm"); an empty binding is better than a wrong one.
  • Integrations (DDI, registries, other EMRs) are mapped at the boundary and must not reshape the core.
  • SDC Questionnaires are an additional authoring/exchange format; they normalise into the internal model, which stays the system of record.
  • Curation or profile labels (e.g. “ABDM-aligned”) are informational until validated; never emit meta.profile or claim conformance without validation.
  • Signed notes are immutable; changes are amendments with a reason. Cases are archived, never deleted.
  • A case pins the version of each element set it applied; updating is an explicit clinician action.
  • Coding is optional in every authoring mode; skipping it never blocks use of an element set. Unverified codes are never emitted as Coding, whichever system they belong to (ADR-003).
  • Registration and other site-specific identity data are never in the marketplace (ADR-004).
  • Marketplace packages are declarative data only — no executable code. Analytics run on the EMR's own engine.
  • Marketplace trust levels are separate, evidence-based labels (checked, tested, reviewed, verified, validated); none implies clinical approval for a given site. The repo never holds patient data.
  • Analytics compatibility is shown with its match kind (exact / via verified code / partial); it is never silently assumed.
  • Suggestions come from deterministic manifest rules; an LLM may only rank or explain, with minimal context.
  • Local content is free; installed marketplace content is read-only, enforced by the server, and extended only by composition or replaced by a newer version. A fork gets a new id and is a local draft.
  • Rules and protocol bands inside any package arrive disabled until a local doctor enables them; seed sets ship with zero rules. An unapproved draft is never applied to a real patient's case.
  • In server mode the signer, approver, reviewer and author always come from the session, never from typed names or request bodies.
  • Every latest value is shown with its age. Summary and lists show data presence, never a judgement on adequacy of care.
  • The AI key lives on the server. AI is off by default and shows exactly what will be sent.
  • Peer review is not regulatory approval; no real patients until the go-live gate is passed.
