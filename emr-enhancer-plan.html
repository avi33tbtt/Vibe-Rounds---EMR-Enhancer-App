EMR Enhancer — Plan

Context-aware, composable clinical documentation with verified coding, FHIR export and a curated content marketplace. Updated 21 Nov 2026. Demo: emr-enhancer.html. Build detail (chunks, prompts, log): emr-enhancer-build-plan.html.

Not for clinical use. Synthetic data only. Generated fields, codes and pathways are drafts until independently reviewed.
Progress

1 · What we are building

A documentation and trajectory layer, not a general hospital EMR. A chart starts blank with a narrative and grows by adding element sets and pathways (disease, care, template). Repeating observations form the patient's trajectory. Codes are verified, notes are signed and amended, and the chart exports as FHIR R4.

Future scope (full EMR direction): patient identity and MRN (p4-5), orders and tests (p5-13), medication administration, ADT and billing (p5-3). Built only after the core proof, in the roadmap order.

Patient journey: 1 Registration (EMR-local) → 2 Clinical recording (marketplace content) → 3 Analytics (marketplace content).

ADR-001 · Internal model + FHIR at the edge

Why. Composition, partial pathways, repeating observations and fast UX are first-class in our model and awkward in SDC or openEHR. Mature systems (OpenMRS, Epic) also keep a rich internal model with standards at the edges.

Rejected. FHIR-native SDC (heavy, poor composition); openEHR archetypes (steep tooling curve).

Consequences. Bindings are {system, code, display} on each field. Verified = code exists on the terminology server and display matches; otherwise it stays text. LLM codes are candidates (source:"llm"); empty is better than wrong. DDI, registries and other EMRs are mapped at the boundary.

Revisit if. A funder or regulator requires Questionnaire as the stored model; cross-vendor content governance becomes the main goal; scope grows to orders, billing and ADT (consider contributing to OpenMRS).

ADR-002 · SDC as an extra authoring format

Does. Import a Questionnaire (paste, file, URL) to an element set; export any set back (original if unmodified); add QuestionnaireResponse to the bundle; re-import of the same URL creates a new version; curation label on imports.

Limits (flagged on import). enableWhen, calculated expressions, value-set options, multi-answer, attachments. Other-system codes are kept but not verified or exported.

ABDM. The ABDM IG defines output profiles (Composition-based records, DocumentBundle), not forms. A form pack can be labelled “ABDM-aligned” but the label is informational; we never emit meta.profile without validation. Real ABDM output is item p5-5 (IG 6.0.0 is the published release; check the current version when started).

ADR-003 · Code-system registry and unified create screen

Decision. Two independent choices on one screen: output (internal set, or also an SDC Questionnaire) and coding (pick systems, or skip). Same picker and verification either way.

  • Skipping coding is first-class: uncoded sets work fully, are flagged “uncoded”, and match analytics by exact id only.
  • Several bindings per field, each verified separately; every verified one goes in code.coding[].
  • Role guard warns on mismatched system (e.g. ICD on a numeric observation); author decides.
  • LLM proposes bindings only for ticked systems. SDC mode lists what SDC cannot yet express before generating.
  • Field model changes binding → bindings[] via a new migration. Do this before the package format is frozen.
  • Terminology host is one allow-listed address from config; public servers are test-only, production needs a configured server with cached results.

ADR-004 · Marketplace by patient journey

StageMarketplace?Reason
RegistrationNoSite-specific identity data; lint rejects it
Clinical recordingYesElement sets, pathways, rules
AnalyticsYesAnalytics depend on elements, not pathways

Orders, MAR, ADT and billing are operational and site-specific: not marketplace content by default.

Content rules

  • Local content is free to edit. Installed content is read-only, enforced by the server; extend by composition or fork (new id, local draft, link to original).
  • Rules and protocol bands arrive disabled; a local doctor enables them (server stamps who/when). Seed sets ship with zero rules.
  • No auto-upgrades; cases keep their pinned version. A withdrawn version warns on existing cases and blocks new use. Nothing is deleted.
  • Unapproved drafts are never applied to real patients.
  • Packages are declarative data only. Analytics run on the EMR's own evaluator; thresholds ship blank with a citation.

Analytics compatibility

  • An analytic declares requires by set+field or by verified code with type and UCUM unit. CI builds an index both ways.
  • Match kinds always shown: exact, via code, partial (missing listed). Units are never converted.

Trust

TierMeaningEditable
Marketplace-verifiedSignature and hash checked at installNo (fork)
Local reviewedApproved by facility informatician; frozenNew draft version
Local draftAI drafts, imports, forks, anything elseYes
  • Index shows checks passed, tests passed, reviewer count and evidence link. “Verified” means peer-reviewed, not regulator-approved.
  • One shared lint script (CI, app, server): schema, SDC structure, bound codes verified, no dose/threshold text without citation, no executable content, no patient-like strings, licence present, hash.
  • Reviewer is never the author; two reviewers for rules, bands or dose-like text; stamped by the server.
  • GitHub gives hosting, history, PR review and CI, not signatures. Each version is pinned by SHA-256 in a signed index; public key pinned in server config; server verifies at install. Protect main; check GitHub's current tag/release protection.

In the EMR

  • Browse: clinical roles. Install: informatician/admin. Doctors request (audited). Site sets minimum tier. File install and private mirror for offline sites.
  • Suggest: deterministic from appliesWhen with redundancy suppression; nothing applied or installed without a click. An LLM may only rank or explain, de-identified, off by default.

Risks. Public repo means no patient data ever. Check SNOMED/ICD/RxNorm/CPT redistribution terms. Distributing decision-support rules may bring medical-device-software duties. Governance (reviewers, conflicts, recall, key rotation) is the real work.

3 · Go-live gate

No real patients until all are true.

  • A named clinician has signed the safety review.
  • A restore from encrypted backup has been tested.
  • Security hardening done (CSP, restricted DB role, cookies, rate limits); safety-test pack passes in CI.
  • Two-browser checks done in real browsers (conflict screen, unsent reading kept across re-login, import report).
  • AI is off by default, server-side only, de-identified, showing exactly what is sent.
  • Device-software and health-data rules checked for the place of use; data-processing agreement for any external model provider.
  • Licences checked for any SNOMED CT, ICD, RxNorm or CPT content shipped.

5 · Invariants

Safety

  • Not for clinical use until reviewed and validated; peer review is not regulatory approval.
  • No LLM-supplied doses, therapeutic thresholds or protocol bands. Doses elsewhere are free text, never calculated.
  • Deterministic logic decides eligibility; AI only ranks, explains or drafts for human approval. AI is off by default; key lives on the server.
  • Latest values show their age; lists show data presence, never a judgement on care.

Data and model

  • Internal element-set/pathway model is the system of record; FHIR is the boundary. Patient-data FHIR is export-only for now; Questionnaire definitions may be imported.
  • Clinical data is never hard-deleted. Signed notes are immutable (amend with reason). Cases are archived, not deleted.
  • A case pins each set's version; updating is an explicit clinician action. A pathway is a starting structure, not a lock-in.
  • Removing a set must not hide recorded data. Values stay stored, but the demo hides them and skips them in the FHIR export. Rule to decide and implement: show a read-only “previously recorded” section and keep it in the export, or block removal once a set has values and require a reason.
  • Signer, approver, reviewer and author come from the session, never typed or sent in a request.

Terminology

  • Verified = exists and display matches. Unverified codes are never emitted as Coding, in any system.
  • Coding is optional everywhere and never blocks use.
  • Profile labels (e.g. “ABDM-aligned”) are informational; no meta.profile without validation.

Content

  • Registration data is never in the marketplace. The repo never holds patient data.
  • Marketplace packages are data only. Installed content is read-only (server-enforced).
  • Rules and bands arrive disabled until a local doctor enables them.
  • Trust labels are separate and evidence-based; none implies approval for a given site. Analytics matches always show their kind.

7 · Stack and MVP slice

Stack. Node.js + PostgreSQL, flat repo root, numbered migrations never edited once applied. Versioned rows with optimistic concurrency, append-only observations and audit, immutable set versions, scrypt hashes, server sessions, CSRF, one permission table on every route, restricted DB role. Browser uses a cache-first store; localStorage only for demo mode.

MVP slice. Synthetic patient with T2DM + CKD 3b + foot ulcer → blank narrative → apply “DM + CKD + Foot Ulcer” → add/remove sets → enter repeating vitals/glucose → verify a few codes → export a bundle coding only verified concepts → case still knows which sets were applied.
