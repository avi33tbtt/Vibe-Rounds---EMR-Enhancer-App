Decision: standalone EMR, no SMART on FHIR. Running as an add-on inside another EMR forces either double data entry or a fragile mapping of that EMR's data into this app's contextual model. The app's value comes from owning its data model, so it is the system of record and the SMART launch, the EMR-read mode and Send-to-EMR are removed. FHIR R4 stays as an export (and SNOMED/LOINC coding stays), so records can leave the system, but nothing is imported from or written to another EMR. Revisit only if a specific hospital integration is ever required; that would be a new, separate project.
Decision: content is local-free, marketplace is read-only (Phase 6). Clinical content (element sets, pathways, rules) follows four rules: (1) local content is free: a facility or clinician can create and edit its own; (2) marketplace content can be fetched and used; (3) installed marketplace content is read-only and is replaced only by a newer published version; (4) it can be extended only by composition, i.e. other marketplace components added next to it, never by editing it. The marketplace is a public GitHub registry (code under MIT). FHIR stays export-only: the marketplace carries content definitions, never patient data, and nothing is read from another EMR. Details in Phase 6 below.
Why the backend work is split into 16 chunks. The prototype reads and writes localStorage synchronously in hundreds of places (cases, sets, codes, bindings, protocols, rules, usage, pins) and keeps repeat readings as arrays inside one case. A server is asynchronous and must let two staff add readings at once. So the order is: schema (repeat rows as their own table) → API with versions → a cache-first client Store (chunk 29, the key step) → shared reference data → import → login → audit. Architecture

  • Today (prototype, chunks 1-25): one HTML file with vanilla JS plus element-sets.js and cds-rules.js as plain script tags. No build step. Data in localStorage; the AI key is pasted by the user into the browser. This is suitable for demos with synthetic data only.
  • Target (Phase 5): browser UI → Express API → PostgreSQL. The server holds the data, sessions, roles, audit log and the AI key. localStorage remains only for Demo mode with synthetic data.
  • Content channel (Phase 6): the server fetches signed, hash-pinned packages from an allow-listed public GitHub registry and stores them read-only. Patient data never travels this way.
  • Validation layer (JS): a bundled table of verified SNOMED/LOINC codes plus schema checks. Anything the model returns that is not in the table is flagged "unverified", never silently trusted.
  • Safety rules carry over unchanged: no clinical thresholds, doses or bands pre-filled; the model never approves a rule; unapproved rules never fire.
Check before publishing. Example codes from older drafts (e.g. SNOMED 20246006, LOINC 89257-3, 32434-6) are not verified, and LLMs commonly invent plausible-looking codes. Look up every code you show in a demo or article in a SNOMED browser (e.g. browser.ihtsdotools.org) and LOINC search (loinc.org), and put only verified ones in the seed table. Keep the "Not for clinical use, synthetic data only" banner until the Phase 5 safety sign-off is complete.

Phase 2: Care-Trajectory, Context-Aware EMR

Idea. Phase 1 went diagnosis → LLM → one disease form. Phase 2 generalises it: the clinician starts a patient with a clean slate (a plain-text case narrative that maps to FHIR) and then adds element sets as the care unfolds: vitals, a basic EMR template, HbA1c monitoring, a sliding-scale insulin chart, or a disease set generated in chunk 2. The sets used most often float to a one-click sidebar. "Context" is an extensible registry (disease and care pathway now; specialty, setting and population later).
  • One concept: Element Set with kind = disease | care | template | custom (and later pathway).
  • Case = narrative + applied sets + values. Additive, so the FHIR builder and analytics iterate over applied sets. Multimorbidity is handled by applying several disease and care sets to one case.
  • Trajectory, not snapshot. Fields can repeat (timestamp + value rows) and get a trend chart, which is what HbA1c and glucose/insulin charting need.
  • Usage ranking is a plain counter (no ML), also ranked by diagnosis.
Safety rules for care sets. (1) The sliding-scale insulin set ships with empty bands; the glucose-to-units table is entered and verified by the clinician or institution, never generated by the LLM. (2) The LLM may suggest which sets to add from the narrative, never doses. (3) Only codes you have looked up yourself go in the verified table. (4) Keep the "Not for clinical use, synthetic data only" banner visible.

Phase 2B: Direct elements (bedside charts, no diagnosis needed)

Idea. Context-aware (disease), trajectory-aware (repeat rows) and pathway-aware routes are the smart routes. The direct route lets a nurse or doctor open a patient and, with no diagnosis, no narrative and no LLM, tap Vitals, Fever chart, HbA1c or Insulin chart and start charting. All built:
  • Quick bar + Today strip (chunk 15). Pinned one-tap buttons independent of ranking and context, with the latest value and its age.
  • Fever chart (chunk 16). Time, temperature (°C or °F per row), route, pulse, antipyretic as free text; multi-day chart, daily max, clinician-entered threshold only.
  • Daily insulin monitoring (chunk 17). Day-by-slot grid with glucose, dose as given and given-by; daily glucose min/max/mean; target range typed by the clinician.
  • Vitals flowsheet + HbA1c due badge (chunk 18).
  • FHIR, analytics and export for all of the above (chunk 19).
Safety rules for direct elements. (1) No thresholds, targets or bands pre-filled; with nothing typed, charts show data only. (2) Dose is free text exactly as given, never calculated, suggested, summed or converted. (3) Views are display-only and never write values. (4) Temperature unit is stored per row; conversion is for display only; FHIR units use UCUM (Cel, [degF]), which you verify yourself. (5) Alerts on these values belong to Phase 4 rules that a clinician approves. (6) Keep the "Not for clinical use" banner.

Phase 3: Pathway-Aware

Idea. A pathway is an element set with kind:'pathway' that lists member sets (e.g. DKA pathway = vitals + HbA1c + sliding scale + daily insulin monitoring + basic EMR template). Applying it adds all member sets in one click, records that the case is on that pathway, and shows a small progress checklist. Chunks 20-22.
  • Additive only. Applying a pathway never deletes values; removing one never removes sets or data.
  • Versioned. The case stores {pathwayId, version, startedAt}.
  • No new engine. The registry, sidebar, FHIR builder and analytics already iterate over sets.
  • Clinician-defined. Seed pathways are skeletons (member lists only); clinicians can save "what I applied to this case" as their own pathway.
Safety rules for pathways. (1) A pathway bundles sets; it never contains doses, bands or thresholds. (2) The LLM may suggest which pathway fits a narrative (ids only). (3) The checklist shows "not started / has data"; it does not claim the care was adequate.

What GitHub does and does not give you. It gives hosting, history, pull-request review, CODEOWNERS, CI and releases. It does not automatically give immutability or signatures: tags can be moved or deleted unless protected, and releases are not signed by default. So the plan does not rely on GitHub for trust: every package version is pinned by SHA-256 in index.json, the index is signed by the registry maintainers, the public key is pinned in the app's server config, and the server verifies both at install.
